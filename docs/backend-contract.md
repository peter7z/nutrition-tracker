# Backend HTTP v1

> **Cambio de producto — 10 de octubre de 2026:** este documento conserva implementación/evidencia del enfoque anterior. El alcance vigente se define en [especificación de producto](product.md) y el backlog: companion iOS de consulta/Salud, registro desde el plugin de ChatGPT y widgets futuros con Extensions. Sus referencias a chat, registro o edición en iOS no son requisitos vigentes. La adaptación del código y de los contratos está pendiente.

Fecha: 2026-10-08. SQLite y FastAPI. Todos los datos privados requieren `Authorization: Bearer <token>`. TLS en producción; HTTP solo loopback en desarrollo. OpenAPI disponible en `/docs` solo en desarrollo.

## Identidad

`POST /v1/auth/signup` y `/v1/auth/login`: `{ "email": "...", "password": "..." }` → `{ "token": "...", "user_id": "UUID", "expires_at": "ISO8601" }`. Contraseña mínima 12 caracteres; token aleatorio expira a los 30 días, hash en servidor. `POST /v1/auth/logout` revoca la sesión. `DELETE /v1/account` borra identidad, sesiones, adjuntos, mensajes y registros propios. No hay recuperación por email implementada.

## Estado y sincronización

`GET /v1/state` → `{ "revision": 0, "records": [{ "id":"UUID", "kind":"entry", "version":1, "payload":{} }], "messages":[] }`.

`POST /v1/sync`: `{ "request_id":"UUID", "base_revision":0, "operations":[{"operation_id":"UUID","action":"upsert","kind":"entry","id":"UUID","expected_version":0,"payload":{}}] }`. `delete` necesita expected_version del registro. La respuesta es `{ "revision":1,"records":[...],"acknowledged_operation_ids":[...] }`. Cambio atómico; HTTP 409 con código `revision_conflict` o `version_conflict` no escribe nada. Reintento idéntico devuelve mismo resultado; reutilizar ID con distinto contenido produce 409. Nunca enviar copia HealthKit por este endpoint. Kind admisibles: `entry`, `day`, `goal`, `product`, `recipe`, `weight`, `activity`, `import`, `profile`, `historical`, `resolution`. Payloads son Codable completos de NutritionModels.swift (fechas ISO8601): entry FoodEntry, day NutritionDayLog, goal NutritionGoalVersion, product FoodProduct, recipe FoodRecipe, weight ManualWeightEntry, activity ManualActivityEntry, import NutritionImportBatch, historical HistoricalNutritionSummary, resolution IntakeResolution, profile NutritionProfile. day/resolution usan ID remoto UUID determinista, manteniendo fecha como payload.id/dayID. Puede enviarse draft solo desde clientes de prueba, pero iOS usa FoodEntry completo. Las versiones de dominio y de servidor son independientes; una modificación no puede reducir la versión de dominio. Las correcciones de cualquier fecha se guardan con versión e historial, sin reapertura. Payload documentado por cliente de dominio; servidor valida tamaños y nutrientes/cantidad no negativos. Totales de ingesta se calculan server-side desde `entry` (nutrients snapshot por cantidad consumida), no desde datos del modelo. Archivos de Salud se mantienen en dispositivo.

`POST /v1/foods` registra de 1 a 20 alimentos consumidos en una operación atómica. Requiere el mismo bearer y recibe `{ "operation_id":"UUID", "base_revision":0, "consumption_text":"...", "foods":[{"name":"Arándanos", "meal":"Merienda", "consumed_at":"2026-10-14T16:00:00-03:00", "serving_size_grams":125, "portion_description":"Arándanos frescos", "nutrients":{"energy":71,"protein":0.9,"carbohydrates":18,"fat":0.4}, "source":"estimate"}] }`. Cada alimento queda como una entrada individual. `nutrients` son el total estimado de esa cantidad en gramos, no valores por 100 g. Todos los elementos deben pertenecer al mismo día local. La respuesta incluye `entry_ids`, las entradas con `draft.amount` en gramos y `totals` por alimento, `receipt`, revisión y `day_summary`; reintentos usan el mismo `operation_id` y cuerpo.

## Chat y propuestas

`POST /v1/chat`: `{ "request_id":"UUID", "day":"YYYY-MM-DD", "text":"...", "health_context":null, "attachment_id":null }`. Objetivos, preferencias, ingesta y últimas entradas se extraen de registros del propietario; no mandar historia entera. Opcional health_context `{ "consent":true,"purpose":"chat","day":"YYYY-MM-DD","metrics":{"weight_kg":72.0,"active_kcal":230.0,"steps":4000} }`: consentimiento específico para esta consulta, sin UUIDs/dispositivo/fuentes/copias crudas. No persiste el contexto de Salud. También admite dietary_kcal/protein_g/carbohydrates_g/fat_g bajo el mismo consentimiento específico; solo se usan como ingesta si la resolución del día seleccionó health. Manual + historical sin resolución explícita produce totales desconocidos y needs_reconciliation. Nunca suma ambas fuentes.

Respuesta `{ "request_id":"UUID", "message":"...", "proposals":[{"operation_id":"UUID", "action":"add|update|delete|query|add_weight|add_activity", "entry_id":null, "expected_version":null, "name":null,"quantity":null,"unit":null,"state":null,"day":"YYYY-MM-DD","nutrients":null,"assumptions":[],"requires_clarification":false}], "totals":{"energy":null,"protein":null,"carbohydrates":null,"fat":null,"saturatedFat":null}, "usage":{"input_tokens":0,"output_tokens":0,"estimated_cost_usd":0,"latency_ms":0} }`. Mutaciones son **propuestas**. Usuario revisa/corrige y confirma enviando operaciones a sync; iOS solo publica estado tras ack. Hypótesis/cena/revisión/fotos/etiquetas no registran consumo automáticamente. IDs estables, idempotencia request+operation y versiones evitan duplicación y corrigen conflictos. El servidor elimina acciones mutantes en consultas hipotéticas detectadas y pide aclaración cuando hay candidatos ambiguos. Nunca dice que guardó una propuesta. Respuesta server incluye acumulado real calculado, no del modelo.

En respuestas de diario, `totals` conserva `null` cuando un nutriente falta en alguna comida. `known_totals` suma los valores disponibles y `nutrient_coverage` expone `knownCount` y `missingCount`; cualquier suma parcial se etiqueta como conocida y se acompaña de las comidas sin ese dato. El chat nunca la presenta como total completo.

`GET /v1/chat/{request_id}` recupera una respuesta completa ya confirmada (chat o review) sin llamar de nuevo al proveedor. UUID ajeno, request fallido o pendiente: 404. Un reintento no cambia contexto ni cuerpo original.

Peso y actividad por chat usan `add_weight`/`add_activity`, con `recorded_at` ISO8601 con timezone, `weight_kg` >0 o `activity_kind` y al menos uno de `duration_minutes`/`active_kcal`. Los campos son nullable; datos ausentes o día ambiguo requieren aclaración. Pasado explícito permite propuesta; planificación o hipótesis no crea operaciones. Confirmación native escribe sólo registros manuales por sync; no crea datos HealthKit.

`POST /v1/review` usa mismo cuerpo con `text` requerido, más opcional `health_review_context`: `{ "consent":true,"purpose":"weekly_review","start_day":"YYYY-MM-DD","end_day":"YYYY-MM-DD","weights":[{"day":"YYYY-MM-DD","kilograms":72}],"daily_nutrition":[{"day":"YYYY-MM-DD","energy":2000,"protein":130}],"daily_activity":[{"day":"YYYY-MM-DD","exercise_minutes":30,"active_kcal":250}] }`. Exactamente ventana de 14 días terminando en day; cada array máximo 14 días únicos. No samples ni IDs/device/source. Valores desconocidos se omiten. Sólo consentimiento de este propósito y esta ventana. El servidor deriva días completos de totales explícitos de día completo o de resúmenes históricos completos; no acepta cobertura declarada por cliente ni infiere completitud del paso de fecha o de comidas registradas. Peso Health consensuado puede aportar una observación por día; no suma ni duplica observaciones manuales del mismo día. Ingesta Health sólo reemplaza totales de los días cuya resolución selecciona health. El contexto no persiste (digest para idempotencia sí).

Respuesta review agrega `review_coverage` {window_days,complete_days,weight_observed_days,complete_days_by_week:[Int],weight_days_by_week:[Int],goal_adjustment_allowed,limitations:[String]} y `goal_proposal` nullable {energy?,protein?,carbohydrates?,fat?,effective_day,rationale,assumptions,requires_confirmation:true}. Guard independiente elimina propuesta de metas salvo ≥10 días completos con kcal/proteína/carbohidratos/grasa conocidos y ≥6 días con peso, con ≥3 en cada semana de siete días. El cliente muestra explicación y aceptar/rechazar; aceptar crea versión de metas mediante sync, nunca una mutación del modelo. No propone metas con fecha anterior al día revisado.

## Fotos

`POST /v1/attachments` multipart `file`: JPEG/PNG/WebP, hasta 10 MB, 20 megapíxeles. HEIC se convierte en iOS antes de subir. Respuesta `{ "id":"UUID", "media_type":"image/jpeg", "width":...,"height":... }`. Solo se almacena una recomposición JPEG sin EXIF/XMP/GPS. GET/DELETE `/v1/attachments/{id}` privados. Chat attachment_id exige propiedad. Propuestas siempre editables y confirmadas; pesos visuales son estimaciones. Fotos enviadas a OpenAI solo tras acción explícita de analizar.

Errores: `{ "error": { "code":"...", "message":"safe generic text" } }`, nunca contenido, fotos, tokens o API key. Sin key/model/costos configurados: 503 `ai_not_configured`, no respuesta inventada. Límites de rate, presupuesto y timeout configurables; error429/503 permite reintento explícito.

## Sincronización nativa y recuperación

TrackingSync conserva checkpoint y journal protegidos por owner+endpoint. Merge de tres vías compara hash de payload del último ack: editar el mismo registro en ambos lados genera conflicto; cambios remotos a registros sin edición local se incorporan. Reintento tras ack perdido usa mismos request/operation UUID. Un journal confirmado se guarda antes de publicar localmente, y recuperación tras falla de escritura no duplica registros. Más de 200 operaciones se envían por batches secuenciales con cursor de revisión e IDs persistidos; cada batch es atómico, el conjunto puede quedar parcialmente guardado remoto si se interrumpe. El cliente no publica una propuesta de asistente hasta completar todos los batches. Lectura manual offline ya está local y muestra pendiente. `conflictReview(store:remote:)` expone sólo registros conflictivos con versiones local/server (nil indica eliminación), owner, endpoint y revisión. `resolve(review,choices:store:remote:)` exige elegir local/server para cada registro, revalida fingerprint local y revisión del servidor, y conserva otras ediciones locales. La elección local incrementa versión de dominio si el servidor avanzó. La propuesta se publica únicamente tras ack. Review vencida o cambio de cuenta exige cargar otra revisión. `replaceLocalWithRemote` sigue disponible sólo para reemplazo integral explícito.

Cambio de alcance del 2026-10-09: el flujo activo no tiene base de alimentos, catálogo ni recetas guardadas. El chat estima automáticamente kcal/macros desde alimento, cantidad y preparación descritos, con supuestos visibles y cantidad editable. Un alimento corriente sin peso puede usar una porción típica explícitamente estimada. Aclaraciones piden datos del alimento/cantidad/preparación, nunca que el usuario ingrese kcal o macros individuales. Correcciones como “eran 100 g” proponen nuevos valores estimados y conservan ID/versión del registro; hipótesis no escriben. La calidad de la estimación depende del proveedor: el backend no reemplaza una IA no disponible con datos inventados.

El schema activo de propuestas no expone product_id/product_version/recipe_id/recipe_version y el contexto del proveedor no contiene catálogos ni recetas. Registros legacy product/recipe, referencias antiguas de ingesta y respuestas ya cacheadas se conservan para sync, backup y compatibilidad; ninguna migración borra esos datos. No hay estado abierto/cerrado: los totales visibles se calculan desde la fuente seleccionada y las comidas históricas se pueden corregir. Al primer registro de un nuevo día, el servidor guarda un snapshot del día anterior; cada corrección posterior agrega una versión. `record_day_totals` guarda un resumen explícito de día completo y una señal de cobertura completa, sin congelar ni bloquear la fecha. Health guardado no contiene datos nutricionales en sync y requiere consentimiento exacto para contexto.

Snapshots Health positivos están prohibidos en cualquier summary histórico, no sólo el último.
